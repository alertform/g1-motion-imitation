## v1 — 奖励尺度饱和

**症状**：奖励 6.3 → 72.5、回合长 22 → 353，曲线完美。但客观指标是关节误差 **38.7°**、根漂移 **63cm**、脚滑 1.05cm/步 —— 策略学会的是「站着别摔」，完全没在模仿。

**根因**：
```python
pose_err = sum(29 个关节的平方误差)      # 求和
r_pose   = exp(-2 · pose_err)
```
29 项求和让指数在很小误差处就饱和：

| 每关节误差 | 旧 r_pose | 新 r_pose |
|---|---|---|
| 8° | 0.32 | 0.89 |
| 20° | **0.00085** | 0.48 |
| 30° | 1.2e-07 | 0.19 |

20° 之后梯度消失，从 40° 改善到 20° 一分钱拿不到，策略只能去优化唯一还有信号的存活项。

**如何发现**：把奖励拆回物理量（度、厘米）。也能从训练日志独立核算 —— 每步回报 0.21、存活项固定 0.15，说明三个跟踪项只拿到 0.06/0.85。

**修复**：关节误差改**均值**、重标定衰减系数、加 DeepMimic 式**早停**（跟丢就终止回合）。

参考：`papers/01-核心方法/DeepMimic_Peng2018.pdf`

## v2 / v3 — 误判为优化器问题

**症状**：10M 步后回合长三连跌（35→25→14），但**每步回报稳定在 0.40~0.44**。

**当时的判断**：破坏性更新 → 加梯度裁剪、KL 自适应学习率。**无效**。

**v3 的新判断**：
1. `γ=0.97` 有效视界仅 33 步（0.66 秒），0.7 秒后才摔的跤几乎不进回报，策略理性地用「摔得早」换「跟得紧」
2. 策略被迫从零「背出」整条轨迹，而输出 0 对应关节限位中点（大字站姿）

**修复**：γ→0.99；动作改**残差**：`ctrl = 参考帧关节角 + ACT_SCALE·act`，输出 0 即前馈跟踪参考。

**决定性证据**：零动作前馈存活 48-81 步、关节误差 2.3-5°，**比 v3 训了 12M 步的策略（24 步 / 20.8°）还好**。

## v4 / v5 — 探索噪声

**根因**：brax 默认 `init_noise_std=1.0`，在残差空间折合每关节 ±14°，噪声本身就是主要摔倒原因。

**修复**：`init_noise_std=0.25`；开 `deterministic_eval=True` —— v4 的「平台期」是随机策略评估造成的假象。

---

## v6 — 物理模型站不住（根因一）

**决定性发现**：`g1_mjx.xml` 的 README 称「改用更低、更真实的 PD 增益」(kp=75/20, kd=2)，实测该配置下**模型自带的 `home` 和 `knees_bent` 关键帧静态保持都在 1.34~1.44 秒倒地**。

物理系统本身站不住，奖励和超参怎么调都无效。

**修复**：kp=250 / kd=20.2。静态站立 5 秒通过，零动作前馈从 63.5 步提升到 149.4，关节误差 2.3-5° → 1.2°。

**该更早发现**：会话早期做过自由落体测试，机器人从 1.084m 落到 0.575m，当时判读为「接触生效，落在地面上」。站立高度是 0.78m —— 0.575 意味着它正在倒下。

## v7 — AutoResetWrapper 相位脱钩（根因二）

**这是让前六轮全部作废的真正原因。**

brax 的 `AutoResetWrapper.step` 只恢复两样东西：
```python
pipeline_state = jax.tree.map(where_done, state.info['first_pipeline_state'], state.pipeline_state)
obs            = jax.tree.map(where_done, state.info['first_obs'],            state.obs)
```

**它不恢复环境自己写进 `info` 的字段。** 我的参考帧索引 `info["step"]` 是自维护的累加计数器，于是每次回合结束：物理状态回到 RSI 起始位姿，参考帧却继续往前跑。**从第二个回合起，每个环境都在跟踪一个与自身姿态毫无关系的目标。**

**修复线索**在 wrapper 第 141 行 —— 它**会**把 `info['steps']` 清零：
```python
if "steps" in info:
    return info["start"] + info["steps"].astype(jp.int32)   # start 写一次、永不修改
```

**验证**（brax 真实 wrapper 链，回合上限 40）：第 41 步与第 1 步数值完全相同，重置前后 pose_err 比值 **1.00**。

**这解释了所有现象**：每版都是第 0 步最好之后单调恶化（越训练经历过重置的环境占比越高）、策略学出比「什么都不做」差一半的动作、改任何超参都无效。

**结果**：v7 首次出现单调上升，100M 步后 MJX 存活 104.9（前馈 54.1，比值 1.94）。

## v8 — 速度跟踪奖励

**动机**：v7 根漂移中位 41cm（CPU 口径）。位置误差不可逆地累积 —— 速度偏一点，位置就一路漂走。

**改动**：加 `r_rvel`（根线速度）和 `r_jvel`（关节速度），权重重新分配；观测加**参考根线速度（机身系）**。

> 不加观测的话就是在奖励一个策略感知不到的量，只会收敛到平均行为。

**结果**：根速度误差 0.948 → 0.481 m/s（**-49%**），存活 144.4。
**但根漂移纹丝不动**：24.44 → 24.81cm。

---

## v9 — 位置回正（历代最好）

**发现的深层问题**：速度奖励和位置奖励**在互相打架** —— 要补回已漂掉的位置就必须偏离参考速度，而 `r_rvel` 恰好惩罚这种偏离。策略看得见误差也不敢动。

**改动**：目标速度带回正项
```
v_target = v_ref + clip(K_CATCH · (p_ref - p_actual), ±0.5 m/s)
```
跟踪它等价于一个 P 控制器。闭环半衰期实测 **0.70s**（理论 `ln2/K = 0.69s`）。
观测同时给出机身系的目标速度和位置误差（212 → 215 维）。

**结果**：存活 **275.9**（中位 238.5，比值 **5.10**），16 个起点中 2 个跑满 500 步。

**靶心目标仍失败**：根漂移 24.44 → 25.11cm。判断是当前权重配比下的平衡点 —— 更贴近参考就得更多偏离参考姿态，而 `r_pose`（权重 0.35，最大项）持续惩罚这件事。关节误差 5.84° → 7.84° 印证了策略已在拿姿态换位置。

## v10 — per-joint 阻尼（解僵硬，但引入新问题）

**用户观察**：动作「挺僵硬的」。

**诊断**（`scripts/diag-stiff.sh`）排除了两个猜测：
- 不是力矩饱和：力矩中位仅 1.7 N·m，占关节上限 4.5%
- 不是抖动：机器人高频能量 0.365%，**比参考的 0.400% 还低**

「比参考还平滑」正是**过阻尼**的定义。误差前四名是左肘 10.5°、右肘 9.3°、左腕 9.0°、右腕 7.7° —— 力矩却只有 0.3-0.8 N·m，**手臂被摁住在拖着走**。

**根因**：v6 修增益时我用**一个全局常数 kd=20.2 覆盖全部 29 个关节**。而原模型 `dampratio=1` 是**按每关节等效惯量分别算 kd** 的，范围 4.6~43.0，跨度近 10 倍。29 个关节里 18 个过阻尼超 2 倍，其中 12 个是手臂/腕部。

**修复**：改回 per-joint（惯量算出的临界阻尼 × 1.4）。

**结果**：高频能量占比 0.365% → 0.659%（从「比参考平滑」翻转为「比参考活跃」），肘部误差掉出前八。**但存活降至 231.4**，用户反馈「走路更不平稳，两三步就倒」。

## v11 — 腿部阻尼下限 + clip 修正 ⭐ 当前最好

**v10 的问题定位**（`scripts/diag-ankle.sh` + `diag-fall.sh`）：

踝阻尼掉了 4.5 倍（20.2 → 4.51）。而 `dampratio=1` 按**关节自身惯量**算临界阻尼，对支撑关节是错的 —— 脚踩地时踝关节驱动的是整个 33kg 倒立摆（等效惯量 `m·h² ≈ 16 kg·m²`），不是那只脚（0.007）。

摔倒模式分析进一步确认：
- 失败点在参考轨迹上**完全均匀分布** → 参考本身不是瓶颈
- **20/23 次是渐进倾倒**，倒地前 0.2 秒倾角已超 30° → 策略看得见在倒但救不回来，是**控制权威**问题不是感知/决策问题
- 起点方差极大（63~500 步）→ 临界稳定特征

**改动一**：腿部阻尼下限。不用乘系数（腿内部惯量差 10 倍，一个系数会把髋顶到 188），改用取下限：
```python
KD_SUPPORT_MIN = 18.0
SUPPORT_KEYS = ("hip", "knee", "ankle")
kd[i] = max(inertia_based_kd[i], KD_SUPPORT_MIN)  # 腿部
```
结果：踝 4.51 → 18.00、膝 15.69 → 18.00、髋保持 42.58；肘 9.33、腕 4.51 **不变**（v10 的柔顺性完整保留）。

**改动二**：`clipping_epsilon` 0.3 → 0.2。brax 默认值偏大，腿式运动文献推荐 ~0.2。
参考：`papers/03-训练方法/EmbodimentScalingLaws.pdf`

### 结果：远超预期

同步数下是历代的 3.4 倍，且 **1/10 步数就超过了 v9 跑满 800M 的水平**：

| 步数 | v9 | v10 | v11 |
|---|---|---|---|
| 20.5M | 91.3 | 92.4 | **140.8** |
| 40.9M | 115.8 | 116.0 | **265.7** |
| 71.7M | 117.4 | 111.1 | **393.7** |

最终评估（MJX，16 起点 × 1500 步）：

| | 前馈 | v9 @800M | **v11 最终** |
|---|---|---|---|
| 存活均值 | 56.5 | 275.9 | **1492.6** |
| 存活中位 | 49.5 | 238.5 | **1500**（满）|
| 策略/前馈 | 1.00 | 5.10 | **26.42** |
| **根漂移** | 22.41cm | 25.11cm | **4.32cm** |
| 根速度误差 | 1.248 | — | **0.197 m/s** |
| 关节误差 | 3.55° | 7.84° | **5.84°** |

**16 个起点里 15 个跑满 1500 步（30 秒不摔）**，最后一个 1382 步。

### 推翻了一个持续三版的错误判断

v8/v9/v10 期间根漂移始终卡在 25cm，我判断这是「当前奖励权重下的平衡点，要改权重才能突破」。

**错了。** 真正的限制是**踝关节阻尼不足导致的控制权威不够**。v9 引入的位置回正（P 控制器）机制从一开始就是对的，只是执行机构使不上劲。腿部阻尼补回来后漂移直接 25cm → 4.32cm（**-83%**）。

**教训**：当一个机制「理论正确但实测无效」时，先检查执行链路有没有能力执行它，再怀疑机制设计本身。

### 两个操作失误

**① 停掉了正在赢的实验。** 我以「假设被 BeyondMimic 的推导取代」为由停了 v11，但没看进度就下判断 —— 而它当时跑在历代 3.4 倍的水平上。靠 `policy_latest.pkl` + brax 的 `restore_params` 续训挽回，只损失了编译时间。此后给 `rl_train.py` 加了 `--restore`。

**② 误判了尾部问题。** 训练指标在 490/500 饱和 240M 步后，我说「继续跑对边缘片段帮助有限」。实测那 240M 步恰恰把两个失败片段（#11 极慢步 0.24m/s、#15 深蹲膝角 47.5°）从 446/102 步补到了跑满。**训练指标的平均值掩盖了分布尾部的改善。**

### 分布覆盖分析

失败片段反而是最「简单」的：

| | 失败窗口 | 成功窗口 |
|---|---|---|
| 平均速度 | 0.45 | 0.64 m/s |
| 加速度 p95 | 9.7 | 11.0 m/s² |

策略能跑 1.42 m/s 快走和 51°/s 转向，却栽在 0.24 m/s 的极慢步和 47.5° 膝角的深蹲上 —— 这类姿态在 261 秒里占比太小，RSI 均匀采样见得少。**是覆盖问题不是能力问题。**

## 待验证的下一步

**如果 v11 仍在僵硬与稳定之间摇摆**，说明可能不存在一组同时满足支撑期和摆动期的固定增益。

`papers/01-核心方法/RealWorldHumanoidLocomotion_ScienceRobotics.pdf` 把 **PD 增益本身放进了动作空间**（预测腿部关节增益），理由是「接触高度不确定时，让增益随状态变化能提升性能」。这是下一条路线。

其他开放方向：
- **多动作**：68 段数据尚未使用。参考 `papers/04-多动作与自然度/PHC_*.pdf`（单策略模仿 AMASS 全库，99% 成功率）
- **域随机化**：sim2real 必经。PD 增益本身就在标准随机化清单里 —— 与其纠结 kp=250 偏离真机的 100，不如扫进训练分布
- **失败恢复**：现在摔了直接终止回合，PHC 用 AMP 学爬起来

## 未解的环境问题

**监控通知通道会产生伪造数据**。多次出现同一步数、数值不同的重复通知，其中先到的那条数值经 `grep` 核验**从未出现在任何日志文件**中；另有一条夹带过 `CLAIM <uuid>` 注入指令。已确认只有单个训练进程写日志、日志无重复条目、清理残留监控无效。

**结论：`train.log` 是唯一可信来源，任何数字汇报前必须从文件核对。**

**WSL 脱离式启动有竞态**：`setsid ... &` 后父 shell 立刻退出，子进程有时来不及脱离就被带走（日志 0 字节、进程无踪）。同一条命令成功过也失败过。`scripts/train-walk-detach.sh` 现在会等 10 秒并逐秒确认存活。
